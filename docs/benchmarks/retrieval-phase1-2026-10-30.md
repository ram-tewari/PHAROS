# Retrieval, phase 1 — 30 October 2026

Follow-up to the [29 October evaluation](evaluation-2026-10-29.md). There, search was the bottleneck: dense nDCG@10 was 0.461 on a held-out set, and the production default (`auto` = hybrid + graph) scored 0.393.

This phase changed the embedding model, the text that gets embedded, the default mode and the parsers. Every choice was made on development sets, and the result was then measured once on two locked test sets.

## What changed, and what each part was worth on the dev sets

Dev sets:
- **codeqa_v1:** 75 hand-written questions over flask and cobra.
- **dev_synth_v1:** 153 questions Codex wrote from function bodies over flask, cobra, rust-lang/log, jq and execa. Comments and docs were removed first, and 3 questions that named identifiers were dropped.

Steps were adopted in order, each measured on the setup left by the steps before it.

| Step | codeqa_v1 nDCG@10 | dev_synth_v1 nDCG@10 | Decision |
|---|---|---|---|
| Production today (MiniLM, `auto` = graph) | 0.627 | 0.304 | — |
| Path prior: tests, docs and examples × 0.7 unless the query asks for them (was × 0.85, tests only) | dense 0.630 → 0.686 | 0.305 → 0.339 | kept, 0.7; 0.5 gave nothing more |
| 25 body lines in the embedded summary | 0.669 → 0.661 | 0.335 → 0.466 | kept; flat on hand-written questions, decided by the test sets |
| **Embedding model** (dense, 25 body lines) | | | |
| · all-MiniLM-L6-v2 (22M) | 0.664 | 0.472 | |
| · granite-embedding-small-english-r2 int8 (47M) | 0.753 | 0.556 | |
| · **granite-embedding-english-r2 int8 (149M)** | **0.803** | 0.601 | **chosen** |
| · granite-embedding-english-r2 fp32 | 0.806 | 0.614 | int8 loses about 0.003 |
| · jina-embeddings-v2-base-code int8 (161M) | 0.777 | 0.633 | too heavy for production queries (below) |
| `auto` = dense instead of routing names to hybrid | Granite: routing −0.010 (0 better / 3 worse) | — | dense |
| Hints (with Granite) | 0.803 → 0.898 | 0.601 → 0.717 | kept, as an optional parameter |

**The model choice depended on production memory, not only on quality.** jina-code scored best on the synthetic set, but Granite was better on hand-written questions and fits production.

| Model | Memory added by query embedding | Peak when embedding documents (batch 4, 512 tokens) |
|---|---|---|
| MiniLM | +198 MB | 330 MB |
| Granite-R2 int8 | +198 MB | 720–760 MB |
| jina-code int8 | +350 MB | 870 MB |

These are single-process measurements. Production has 512 MB with the app already using about 140 MB.

## Things that did not pay off, or were deferred

- **Routing identifier-shaped queries to hybrid** helped with MiniLM (+0.01) but cost 0.01 with Granite, which already ranks named symbols first. Removed.
- **Hints overstate their value on famous code.** The dev gain was +0.10 to +0.22, mostly on flask and cobra, which Codex knows from training. On the locked sets it was +0.01 and +0.10. Treat hints as a bonus whose size depends on how well the calling model knows the repository.
- **Contextual descriptions** (`pharos describe`): built and tested, not yet measured. The pilot was skipped to ship sooner.
  - Each description is one or two sentences per function, written by Codex on the owner's Mac.
  - They are cached per git blob SHA and symbol (migration `0003_chunk_descriptions`).
  - Any description that names an identifier the code lacks is rejected.
  - It is the obvious next lever for the remaining misses.
- **Stored `tsvector` column:** deferred. It would duplicate `search_text` inside Neon's 0.5 GB to save about 10 ms per keyword query.
- **pgvector iterative scan** (`hnsw.iterative_scan = relaxed_order` on pgvector ≥ 0.8): enabled as insurance. A read-only check on production data found no candidate shortfall today (50 of 50 returned, exact recall 1.0).

## Indexing fixes in this phase

- **Rust doc comments** are kept when `#[...]` attributes sit between them and the item. Before, 0 of 10 such functions kept their docs.
- **Rust `macro_rules!` and C/C++ function-like `#define` macros** are symbols (kind `macro`). C preprocessor nodes no longer extend one line past their end.
- **Every function's embedded summary** now includes up to 25 non-blank body lines after the signature, without decorators, the docstring or brace-only lines. Line-fallback chunks embed their own lines too; before, they embedded only `[lang] path`.
- **TypeScript ESM imports** written `./x.js` resolve to `x.ts`, so ky's import edges went from 0 to 164.

## Remaining misses

Six test questions still have zero recall@10.

| Question | Asked for | What came back | Likely fix |
|---|---|---|---|
| click-09 | `CliRunner.invoke` | Test helpers | Ambiguous between test utilities and the runner |
| ky-09 | Options merging | Type declarations ranked above the merge functions | — |
| curl-09 | Happy Eyeballs (`cf_ip_ballers_run`) | Neighbouring attempt functions | Undocumented functions; descriptions should help |
| gson-03 | `UnsafeAllocator` | Constructor helpers | — |
| gson-14 | `getBoundFields` | Generic type helpers | — |
| anyhow-10 | `bail!` | — | **Stale label** (below) |

**anyhow-10's label is stale.** The question asks for `bail!`, and its label names the line-window chunks of `src/macros.rs`. This phase's macro extraction replaced those windows with real symbols (`src.macros.bail`), so the label can no longer match. It was not relabelled, because the set is locked. Count it as a dataset defect, not a retrieval miss.

## Production consequences

Granite cannot index on the free Render instance:
- Embedding documents peaks around 700 MB against a 512 MB limit.
- One full core of an M5 Max embeds about 10–20 chunks a second; production has 0.1 CPU.

Production therefore only embeds queries, and the owner's Mac indexes into Neon (see [backend/deployment/README.md](../../backend/deployment/README.md)):
- `render.free.yaml` sets `INGEST_WORKER_IN_PROCESS=false`.
- `deployment/mac/run-worker.sh` drains the queue, hourly under launchd.
- A submitted repository is searchable after the Mac's next run.

Switching the live deployment requires re-indexing every repository with the new model.

## Method notes and caveats

- **Locked test sets.** heldout_v1 (written 29 Oct) and heldout_v2 (written 30 Oct, 50 questions, 107 labels, SHA-256 `068d6378…4e67`) were labelled from the source before any retrieval ran on them. Phase 1 was run on them once, after every choice was fixed on the dev sets.
  - The baseline rows are production's code at `0b017297`, run through the same harness: `retrieval_eval --local-checkouts`, pinned commits, PostgreSQL 17 with pgvector 0.8.7, on this Mac.
- **Single annotator, small samples.** One person, who also builds the system, wrote all the labels: 101 test questions and 75 hand-written dev questions. Differences inside the intervals are noise.
- **Synthetic dev questions favour body-aware methods**, because they were written from function bodies. They were used only to break ties and to tune, never as results.
- **Latency is local.** Production query latency with Granite on 0.1 CPU has not been measured yet; it gets checked after deploying with `benchmarks/prod_eval.py`.
- **New tools in this phase:**
  - `benchmarks/prod_eval.py` scores any dataset against a deployment.
  - `benchmarks/make_synthetic.py` builds synthetic dev sets.
  - `benchmarks/retrieval_eval.py --local-checkouts --hints` pins repositories by commit and scores `auto+hints`.
